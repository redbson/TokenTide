# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## Current product direction

- The product is named TokenTide. Earlier names (Usage Monitor, Tandem, TokenBar) are retired; TokenBar in particular is already used by many public projects. The logo is a "T" (for Token) monogram built from two quota bars (blue top bar = Codex, orange stem = Claude Code) on a dark rounded square. Avoid concentric rings — they read as Apple's Activity rings; keep the icon, favicon, and menu-bar glyph consistent with `branding/tokentide-icon.svg`. The bundle identifier stays `local.usage-monitor` so WebKit local storage survives.
- The product is a menu-bar widget: a borderless dark dropdown panel (360px wide) under the status item, modeled on compact macOS menu-bar utility panels such as Tencent Lemon. Do not bring back a standalone window or full-page layout.
- The 历史 tab starts with usage records modeled on Claude Code's `/stats` (provider switch, 概览 / 模型 / 使用率, 全部 / 90 天 / 30 天 / 7 天, eight stat cards, a 26-week heatmap, a book comparison), followed by the quota trend. 使用率 shows weekly quota utilization: one bar per weekly window (peak usage before reset), average / peak / full weeks / this week. Codex weeks come from rollout `rate_limits`; Claude Code weeks come from TokenTide's own log (`server/quota-weeks.mjs`); weeks before it are estimated from local transcript usage weighted by API prices and calibrated on recorded weeks, drawn as hollow bars with "≈" figures. Never present estimates as recorded values. Codex windows that only ever read 0% with a reset about seven days after the reading are idle readings before a week started (`isIdleWindow` in `src/stats-format.js`) and never count as weeks. A week whose next week began at least 12 hours before its due reset, with its own readings stopped by then, was reset early by the tool (`findEarlyResets`): it keeps its own peak, gets a small dot under its bar (in a row laid out like the bars) with a legend entry, its tooltip shows when it actually ended, and the note counts them. Up to 12 bars spread across the width with a date under each (`BarChart` in `src/UsageStats.jsx`); more pack to the right with dates at both ends. The 7-day range shows this week instead: used, projected at the current pace (dashed outline), last week, and the reset date; for Qoder it shows credits per day.
- Panel anatomy: tabs (额度 / 历史 / 设置) with an orange underline, compact provider blocks (icon, name, connection line, large remaining %, thin progress bar, per-window rows), an inline dismissible banner for low quota or errors, and a darker footer bar. The 设置 tab holds grouped toggle rows: 开机时启动 (SMAppService login item via the native bridge: `getLoginItem` / `setLoginItem` / `openLoginItems`, answered with a `usage-monitor:login-item` event), 自动刷新, and 低额度提醒. UI copy is bilingual: every string lives in `src/i18n.js` in both Chinese and English (English may add `.one` singulars). The language follows the Mac (Chinese when the primary system language is Chinese, English otherwise) unless chosen in 设置 → 语言; the native shell mirrors it for the menu, tooltips, and loading screens.
- The status item has two styles (`menuBarStyle` in the panel settings, sent with the `summary` message as `style`; macOS only, since the Windows tray icon is always bars): `detailed` draws two-line columns of each provider's current-window remaining percentage (`CX` / `CC`, then `QD`); `compact` draws a small gauge: one vertical bar per provider, filled from the bottom, inside a thin rounded frame 19 pt tall (about 23 pt wide for three tools; 2 pt bars 4 pt apart, with matching side padding; 14 pt of travel so a 10% difference shows; horizontal bars were tried first and read as a ☰ menu icon when full). The tooltip always lists every shown provider's remaining quota.
- Qoder credits come from the Qoder CLI's `get_usage_info` control request (`server/qoder-usage.mjs`); never read Qoder's own stored credentials. Qoder is hidden (`installed: false`) unless the Qoder app or CLI exists. Its headline counts only the account's own credits (plan and add-on); the org resource package is shared by the team, so it has its own row and never counts toward the headline, menu-bar value, or low-quota notice. In History, Qoder transcripts (`~/.qoder/projects`, Claude Code format) are measured in credits — they report zero tokens — and its Utilization view shows credits per week.
- Reading reliability: Qoder is started with `--strict-mcp-config --no-session-persistence` (no MCP servers: 3–6 s instead of 10–40 s), falling back to plain flags if an older qodercli exits on them. Codex's own request to chatgpt.com fails or stalls now and then ("Codex could not reach its server just now"), so Codex and Qoder reads are retried once after 1.5 s (coded errors are not). A failed read that is likely temporary shows the tool's last successful reading instead (`withLastReading`: `stale: true`, `readAt`, amber dot, "暂未刷新 · N 分钟前的数据"), at most 30 minutes old and never across a window reset; signed-out, no-plan and missing-CLI errors show as they are. Stale readings are real readings from the tool, never invented, and do not go into the weekly log or the quota trend.
- Refresh tiers: each kind of data has its own pace. Quota left and current usage (and DeepSeek Harness local usage, which rides along) are read every minute while the panel is open, on opening if older than 30 s, and every `quotaInterval` minutes (1/2/5/10, default 2) while only the menu bar or tray shows them; the shells send `usage-monitor:show` / `usage-monitor:hide` so the page knows. `autoRefresh` off means open-or-button only. The DeepSeek balance (a network request) is reused for 5 minutes unless the read is forced (`/api/usage?force=1`: the refresh button, a new key). History and stats (`/api/stats?maxAge=<s>`) are counted again only when History is open and the last count is older than `statsInterval` minutes (15/30/60, default 30), or on Recount / the refresh button; quota refreshes never trigger a recount. DeepSeek prices are checked once a day. A quota read costs about 7 s of CLI work, a warm history count well under a second.
- Provider notices come from coded errors (`errorCode`, translated as `providerError.<code>`): `qoderCliMissing`, `claudeSignedOut`, `claudeNoPlan`, `claudeTemporary`. When get_usage has no plan limits, the service asks `claude auth status --json` why; a signed-in claude.ai account is retried once before the `/usage` fallback. `claudeSignedOut` shows a sign-in button that posts `{ type: "signIn", tool }`; the macOS shell opens a `.command` file in Terminal (no Automation prompt), the Windows shell a console window, each running the tool's own login command.
- Settings → Shown tools stores `hiddenProviders` in the page's settings; a hidden tool is still read by the service but left out of the Quota tab, header count, menu-bar summary, low-quota notices, and History. At least one installed tool stays on.
- Windows (preview) is a tray app built with Electron in `windows/`: `main.mjs` (tray, borderless panel above the taskbar, bridge, launch at login via the Run key), `preload.cjs` (exposes `window.tokentideNative.postMessage` and `window.__TOKENTIDE__ = { platform: "windows", systemLanguages }`), `tray-icon.mjs` (one bar per shown tool, drawn as PNG without a canvas; tooltip has the numbers), and `updater.mjs`. It speaks the same bridge messages and `usage-monitor:*` events as the macOS shell. Page copy that names the Mac, the menu bar, or Login Items gets a Windows wording in `PLATFORM_MESSAGES.windows` (`src/i18n.js`). The service starts CLIs through `server/commands.mjs` (PATHEXT lookup, npm `.cmd` shims via cmd.exe, whole-tree kill); the expect-based Claude `/usage` fallback is macOS-only.
- DeepSeek usage comes from DeepSeek Harness's session logs (`$DSH_HOME/sessions`, default `~/.dsh/sessions`; `server/deepseek-usage.mjs`, `aggregateDeepseekSession` in `server/usage-stats.mjs`). Each session directory holds one log per format generation (`session[.vN].jsonl[.zstd]`); read only the highest. Compressed logs are several Zstandard frames, one per write batch, and Node's decoder stops after the first, so frames are split by hand (`zstdFrameLength`) and a torn final frame is left for the next read. Tokens follow Harness's token meter (`usage` on `assistant/message` / `assistant/attempt`, last sample per turn and step, `llm/retry-started` starts a new attempt), the model comes from `request/context`, and sessions with a `parentSession` are subagents. DeepSeek is pay-as-you-go: its card (`provider.usage`, `isUsageOnly`) shows tokens today / 7 / 30 days instead of a percentage, it stays out of the menu bar, the quota trend and low notices, and History has no Utilization view for it. Never read Harness's `.credentials.yaml` or its local API. The API balance comes only from an API key the user saves in Settings (`/api/deepseek-key`: PUT checks it with DeepSeek before saving, DELETE removes it, GET returns only `maskSecret` — the key itself never goes back to the panel or a log). Keys live in `server/secret-store.mjs`: the login Keychain via `security -i` with the command on stdin (never in argv) on macOS, DPAPI via PowerShell stdin on Windows. The balance is `GET https://api.deepseek.com/user/balance` (CNY preferred); readings go to `deepseek-balance.json` only when they change, and spending is the sum of drops (rises are top-ups) — it covers the whole account, so say so in the UI. A new or removed key clears the readings. The card leads with the balance when there is one; Harness usage also carries an estimated cost (`server/deepseek-pricing.mjs`: DeepSeek's published yuan-per-million prices, peak = weekdays 9–12 and 14–18 Beijing time, off-peak half, priced per reply at its own time; unlisted models get no cost). Always label it as an estimate (约 / ≈, with the tooltip, which says when the prices were last checked). Prices refresh themselves (`server/deepseek-price-book.mjs`): at most once a day, and only while DeepSeek is shown (Harness installed and not in the panel's `hiddenProviders`, which the panel passes as `/api/usage?hidden=`), the service fetches DeepSeek's public pricing page (`https://api-docs.deepseek.com/zh-cn/quick_start/pricing/`, plain GET, 10 s timeout, no key, cookie or account data), reads the price table, and uses it only if every model has all three peak prices and each off-peak price is half its peak; good tables go to `deepseek-prices.json` with their check time. Never invent prices: a failed fetch or parse keeps the last good table, and with none the built-in table in `server/deepseek-pricing.mjs` applies — still update it and its date when DeepSeek changes prices. Cached DeepSeek costs (the reader's and the History cache) carry the table's `version` and are priced again when it changes. The card's periods and History's Overview (instead of the longest streak) show it. History's DeepSeek tab has a Balance view instead of Utilization, ending with the spending record (`dailyLedger`: per local day the balance moved, spent / added / closing balance, newest first; a drop seen after the app was off is attributed to the day of the reading that saw it). The balance request and the pricing-page check are the product's only outbound requests of their own: the balance must stay opt-in (only with a saved key), and the pricing check must stay limited to while DeepSeek is shown, once a day, with no credentials sent.
- Keep the product focused on the remaining local quota for Codex, Claude Code, and Qoder, plus DeepSeek Harness token usage. Do not add agent workflows, logs, CPU/memory telemetry, or a navigation sidebar.
- Quota values must come from the locally signed-in tools. Show an unavailable state instead of invented fallback numbers.
- Never return or log tokens, credentials, or unmasked account identifiers from the local usage bridge.

The service listens on 127.0.0.1:46173 (`APP_PORT` in `server/storage-migration.mjs`); before 0.6.3 it was 4173, Vite's `vite preview` default, which other projects kept killing. Shells load the panel only after `/api/health` answers `{ app: "tokentide" }`, so another program on the port is never shown. Until the shell records `storageMigrated`, it starts the service with `--legacy-port 4173`: the service briefly serves a hand-over page on the old origin that posts that origin's localStorage (settings, quota trend) to the service, and the new origin's page imports it once from `/api/migration`. The shells keep the local service alive: if it exits (crash or killed), they restart it with a growing delay (up to five tries, reset after five minutes of healthy running), and the panel posts `serviceUnreachable` when its own request is refused so the shell can bring the service back and reload the page.

Packaging: `npm run build:mac` bundles the Swift shell (`macos/*.swift`), the built panel (`dist/client`), and the Node-only service (`server/*.mjs`, entry `server/main.mjs`, port 46173) into a self-contained `release/TokenTide.app`; the service must keep using Node built-ins only. `npm run dev` (Vite, port 5173) is for development and shares the API via `server/api.mjs`. Publishing a GitHub release `vX.Y.Z` runs `.github/workflows/release.yml`, which attaches `TokenTide-X.Y.Z.zip`, `.sha256`, and an unversioned `TokenTide.zip` (README download link); `macos/Updater.swift` depends on those exact asset names and verifies checksum, bundle identifier, version, and code signature before swapping the app. The same release gets `TokenTide-Setup-X.Y.Z.exe`, its `.sha256`, and `TokenTide-Setup.exe` from `scripts/build-windows.mjs` (electron-builder, per-user NSIS installer, x64; Electron tooling lives in `windows/package.json`); `windows/updater.mjs` depends on those names, verifies the checksum, and runs the installer with `/S --updated --force-run`. On Windows the service runs in an Electron utility process (Electron's Node), so users need no Node.js. `.github/workflows/windows.yml` checks it on a Windows runner: tests, installer build, silent install, and a `--smoke-test` run against stand-in `.cmd` CLIs from `tests/fixtures/`.
